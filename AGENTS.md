# AGENTS.md\n\n# RustDesk Custom — AI Agent Operating Contract\n\nThis file is the operating contract for AI coding agents working in billradar/rustdesk-custom. Read it before modifying the repository. Repository rules are enforced by CI where possible; do not rely on memory or assumptions.\n\n## 1. Project\n\nbillradar/rustdesk-custom is a maintained, reproducible and auditable customization and release repository derived from upstream RustDesk.\n\nIt exists to maintain controlled customizations and patchsets, integrate upstream revisions, build supported platforms, validate compatibility, qualify artifacts, maintain Standard and SOS variants, support Android production signing, and provide reproducible GitHub Actions based release workflows.\n\nThis is an engineering and release system, not a disposable source fork.\n\n## 2. Current state\n\nThe repository has already undergone substantial normalization:\n- functional repository architecture and repository-contract validation;\n- documentation-aware change classification;\n- documentation-only CI separation;\n- workflow-dispatch input clarification;\n- upstream compatibility and validation flow improvements;\n- cross-platform build validation;\n- Android ARM64, ARMv7 and x64 build support;\n- Android production-signing migration and security gates;\n- YubiKey hardware-signing validation;\n- production credential leakage scanning;\n- artifact and release qualification checks.\n\nDo not undo these protections merely to make a local task easier.\n\n## 3. Functional architecture\n\nFunctional areas include .github/workflows, .github/actions, scripts, validation, build/release logic, metadata, patchsets, platform definitions, tools, dependency declarations, packaging inputs, signing and qualification inputs.\n\nDocumentation is not functional architecture. Normal documentation includes README.md, README.*.md, docs/, CHANGELOG files, LICENSE files, issue/PR templates, CODEOWNERS, SECURITY.md and .gitignore.\n\nREADME.md and README.zh-CN.md are valid root landing pages and must not be moved into docs merely to satisfy an artificial architecture rule.\n\nThe repository contract validates functional architecture. It must not become a documentation linter.\n\n## 4. Change classification\n\nClassification is fail-closed:\n\nALL changed files non-functional => DOCS_ONLY.\nANY functional or ambiguous file => FUNCTIONAL.\n\nExamples of functional changes include .github/workflows/**, .github/actions/**, scripts/**, metadata/**, patchsets/**, build/**, platform/**, tools/** and requirements.txt.\n\nA PR containing both documentation and a workflow/script/build change is FUNCTIONAL.\n\nDOCS_ONLY changes may use lightweight validation and must not unnecessarily run full builds, compatibility qualification, production signing or production release jobs.\n\nDo not use workflow paths-ignore in a way that leaves required checks permanently pending.\n\n## 5. Branch model\n\nmain = stable integration and release baseline.\ntest/development = shared development and integration branch.\n\nDevelopment should derive from main. At the beginning of a new cycle, prefer main and test/development to be synchronized. New work then accumulates on test/development until it is accepted into main.\n\nGit history is audit data. It must remain possible to determine which development commits entered main.\n\n## 6. Git history rules\n\nFor test/development -> main, prefer a normal merge commit. Do not normally squash-merge the long-lived development branch.\n\nDo not rebase a shared public test/development branch merely to make history look cleaner.\n\nNever use file-tree equality as a substitute for Git ancestry. Two branches may contain identical files while having different histories.\n\nWhen determining whether work has reached main, inspect merge-base, commit ancestry, ahead/behind counts and the relevant commits.\n\nNever perform reset --hard, force push, force-with-lease, rebase, history rewrite or branch-ref replacement on main or test/development without explicit authorization.\n\nBefore a history rewrite, determine the current heads, merge base, unique commits, tree equality, whether the branch is shared, and whether rewriting is explicitly authorized.\n\n## 7. Pull requests\n\nFunctional PRs must explain what changed, why, affected functional areas, validation performed, CI impact, release impact and signing impact where relevant.\n\nDocumentation-only PRs should remain lightweight.\n\nDo not introduce functional dependencies or build complexity merely to validate documentation.\n\n## 8. CI rules\n\nCI is part of the functional architecture.\n\nExisting manual workflow inputs are part of the CI interface. Do not silently rename, remove or change their semantics. Existing controls include upstream_ref, force_rebuild and promote_stable.\n\nforce_rebuild explicitly forces the functional/full path.\n\nCI must enforce repository policy rather than merely report it.\n\nDo not weaken a failing security, compatibility or qualification gate simply to obtain a green workflow.\n\n## 9. Upstream and patchsets\n\nUpstream RustDesk integration must remain explicit and reproducible.\n\nDo not bypass patch application, remove compatibility validation, silently replace upstream source, or hard-code an upstream revision solely to make CI pass.\n\npatchsets are functional inputs. When changing them, identify the affected upstream revision, verify patch application, run relevant validation, inspect the resulting diff and preserve reproducibility.\n\n## 10. Release and signing security\n\nProduction release qualification is a hard boundary. Do not skip required validation, weaken artifact checks, accept test fixtures as production payloads, or silently change release semantics.\n\nNever commit keystores, private signing keys, production passwords, key passwords, YubiKey PINs, PKCS#11 credentials or other production signing secrets.\n\nProduction Android signing must remain explicitly authorized. Normal CI must not unexpectedly perform hardware-backed production signing.\n\nDo not print credentials or sensitive signing material to logs.\n\nYubiKey/PKCS#11 operations are privileged. Do not bypass preflight, replace hardware signing with a hidden software key, expose PINs, or alter signing gates merely to obtain PASS.\n\nBuild success and production-signing success are separate states.\n\n## 11. Supported platforms\n\nPreviously validated target families include Windows x64, Linux x64, Linux ARM64, macOS Intel, macOS ARM64, Android ARM64, Android ARMv7 and Android x64.\n\nAndroid build support and Android production-signing identity are separate concerns. Never claim production signing support merely because an Android build succeeds.\n\n## 12. Naming and dependencies\n\nUse stable semantic names for permanent functionality. Temporary phase names such as phase5.py or phase5-fix.py should not become permanent architecture when a functional name is appropriate.\n\nPrefer semantic names such as change_classification.py, repository_contract.py, build_metadata.py and release_validation.py.\n\nUse requirements.txt for Python dependencies required by repository tooling. Do not create temporary dependency files.\n\nDo not add unnecessary dependencies for documentation-only work.\n\n## 13. AI operating procedure\n\nBefore modifying the repository:\n1. Inspect the current branch and Git status.\n2. Identify the current HEAD.\n3. Understand the requested scope.\n4. Inspect relevant existing files and CI rules.\n5. Classify the change as DOCS_ONLY or FUNCTIONAL.\n6. Inspect main/test/development ancestry when branch state matters.\n7. Make the smallest coherent change.\n8. Validate the result.\n9. Inspect the final diff.\n10. Report exactly what changed and what was actually verified.\n\nNever claim that CI passed, a PR merged, a release was created, an artifact uploaded, a branch synchronized or a signature validated unless repository state confirms it.\n\nDo not invent repository state from conversation history.\n\n## 14. Avoid unrelated refactoring\n\nWhen asked to fix one issue, do not automatically rewrite unrelated workflows, rename unrelated files, reorganize the repository, alter release behavior, modify signing behavior, change upstream resolution or remove functionality.\n\nLarge architectural changes require explicit scope.\n\n## 15. Core principles\n\n1. Preserve existing behavior.\n2. Preserve Git history.\n3. Preserve security boundaries.\n4. Prefer explicit validation over assumptions.\n5. Prefer the smallest coherent change.\n6. Fail closed when classification or safety is ambiguous.\n7. Ask for authorization before destructive operations.\n8. Never claim an unverified repository state.\n\nThe repository should remain reproducible, auditable, maintainable, secure, CI-enforced, upstream-aware, release-safe and AI-operable.\n\nThis file is an operating contract, not a suggestion.
