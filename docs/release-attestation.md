# Release inventory and Sigstore attestation

New Tag and Nightly releases use exactly two public metadata files:

- `update-manifest.json`: deterministic `rustdesk-release-manifest-v2` inventory,
  with upstream version/SHA, custom repository SHA, patchset and Common/SOS hashes,
  numeric repository/owner IDs, preparation/build run, build options and recomputed
  identity, channel and Stable patch revision. Each installer has a name,
  size, SHA256 and unique OS/architecture/variant/flavor/package selector.
- `release-attestation.json`: standard Sigstore bundle generated by pinned
  `actions/attest-build-provenance`, with a SLSA v1 provenance statement whose
  subject is the exact SHA256 of `update-manifest.json`. This transitively binds
  every installer digest and selector in the manifest. Do not handcraft or edit
  this bundle after signing.

Public `SHA256SUMS` is removed directly, without a fallback or dual-write period.
Missing JSON, invalid signatures, unsupported verification tools, malformed or
ambiguous manifests, changed bytes and incomplete inventories stop release
creation/publication/reuse. Old checksum-only Drafts are not publishable by the
new verifier. Existing tags and Releases are never renamed, rebuilt, supplemented
or overwritten to work around this rule; a collision still requires review.

## Proof production and verification

Only the aggregation jobs receive OIDC and Attestations write permissions. The
attestation step runs only for the main workflow-dispatch draft/release path,
after package and provenance qualification. Dry-run and ordinary CI do not mint
proofs. No private signing key, release App token or Android signing credential
is given to the attestation action. It does not sign application executables or
replace Android v2/v3 signing checks.

Release write jobs download the newest same-run proof artifact (the two JSON files only), revalidate the
package matrix and regenerate the manifest from validated package identities.
Before the first Release/tag write they verify that regenerated manifest against
the downloaded bundle using `gh attestation verify --bundle`. Policy requires:

- this repository and its exact `tag.yml` or `nightly.yml` signer workflow;
- source ref `refs/heads/main` and the manifest's exact custom commit SHA;
- GitHub-hosted runners and SLSA v1 provenance;
- the current run/source identity and exact package bytes/size/digests;
- certificate numeric repository/owner IDs, dispatch trigger and exact invocation
  run, with provenance builder/run agreeing with the certificate.

Stable and Nightly existing-release verification downloads both JSON assets by their verified
GitHub asset IDs, checks their GitHub digests and sizes, verifies the signature,
and compares all installer metadata to the attested inventory. It also binds the
manifest to the preflight's upstream/custom SHAs, patchset and patch hashes.
An `untagged-*` Draft alias never determines which bytes to download.

The runner must provide a GitHub CLI supporting `gh attestation verify` and the
listed policy flags. An older CLI fails closed. Actual OIDC issuance, Sigstore
signing and full hosted-run verification require a workflow run on the intended
main commit; local mocked contracts do not establish those outcomes.

## Relation to GitHub Release attestations

The reference `application/vnd.dev.sigstore.bundle.v0.3+json` file supplied during
review contains an in-toto Release v0.2 statement signed by GitHub, binding a
repository, tag and package hash. Its outer Sigstore/DSSE structure is a useful
reference; its certificate/signature, repository identities and digests cannot
be reused here. Decoding a payload is not cryptographic verification.

This implementation uses build provenance rather than GitHub's automatically
generated immutable-Release statement. Build proofs can be generated and
verified before publishing a Draft and work with Nightly's existing moving tag.
It does not enable immutable releases, freeze Nightly tags, or claim that a Draft
already has GitHub's post-publication Release proof.

## Client boundary and internal artifacts

Current v3.3 clients consume and verify the same schema-v2 manifest using the
patch-carried native Sigstore verifier. They require a published Stable release,
strict typed selectors and exact API inventory; they never parse Release body.
Historical v1/v2 and v3.1/v3.2 binaries keep their old behavior and need a manual
upgrade. No old schema/body fallback or historical patch rewrite is provided.
See [Client updates](client-updates.md).

Release notes contain upstream notes, human customization changes and links.
Source IDs, hashes, asset inventories, compatibility audit evidence and completion
markers live in machine JSON/proofs and repository audit records. Stable reuse,
existing-Draft promotion, Nightly ownership/reuse and cleanup verify JSON before
writes; prose cannot grant ownership or override identity. Missing/legacy JSON
fails closed, including old Nightly objects that require explicit migration review.
A Draft refresh rechecks unchanged API state and its proof immediately before
deletion. Publication remains a separate explicit operation.

Internal source bundles, per-target build artifacts and historical fixed-release
audit tools retain their existing checksum manifests; these are not public
Release inventories and are outside this format switch.

Run `python3 -m scripts.release.attestation_contract` and the affected release,
Nightly, Profile and repository architecture contracts after changing this path.

The local crypto regression uses genuine schema-v1 metadata from CD 43146078797
only to test the cryptographic layer. The schema-v2 parser/selector fixture is
unsigned and is rejected with that old proof. This is not evidence of a fresh
schema-v2 signed build; hosted CD on the final main commit remains required.

One presentation-only edit of the existing v3.1 Draft hides its original metadata
in an HTML comment so old parser semantics and provenance remain available. It
does not convert that historical manifest or grant it schema-v2 admission. New
release bodies have no hidden machine block. Editing a private GitHub Draft can
regenerate `untagged-*` download aliases; verified asset IDs/digests and the real
Git tag remain the identity, and write operations explicitly carry tag/source.

The configured Android signing toggle remains part of a dry-run manifest's build
identity even though dry-run does not access production signing. Schema validation
permits that unsigned build-only inventory; local proof attachment and remote
release reuse still require all three production signatures when signing is
configured. Such dry-run inventories are never attested or published.
