# Client updates

Both Common patch generations include `0005-custom-release-updates.patch`.
All custom clients, including builds made from upstream Nightly, query only
`https://api.github.com/repos/billradar/rustdesk-custom/releases/latest`.
There is no client Nightly update channel, beta checkbox, embedded GitHub token,
or official-server fallback. The upstream Nightly monitor and build/release
workflows remain intact.

## Identity and ordering

Prepared source embeds `src/custom_update/build.json` before inventory is frozen.
Its manifest binds the file to the version, upstream SHA, variant and prepare run.
Stable preparation receives the patch revision selected by Tag preflight; it must
not invent one. About displays `1.5.1-custom.v2.6`, for example. Non-release
builds display `1.5.1-custom.build123` and do not claim a Stable revision.
Native package-manager versions are unchanged.

Stable tags are compared numerically: upstream version, patch generation, then
revision. `v2.10` is newer than `v2.9`; a higher revision cannot downgrade the
upstream version. A non-release client may move to Stable at the same version
only when upstream SHAs agree; otherwise it waits for a higher upstream version.
This avoids guessing the chronology of different Nightly/Stable source commits.

## Integrity and installer boundary

No additional update manifest is needed in this phase. Read the existing tag,
repository-owned completed-release metadata, and Release asset API. Reject drafts,
prereleases, malformed tags, incomplete metadata, missing/duplicate packages,
foreign URLs, and assets without an uploaded state, bounded size and SHA256 digest.
Package matching includes OS, architecture, Standard/SOS, normal/DRM Wayland, and
DEB/RPM/SUSE-RPM or Windows EXE/MSI format. Unknown package formats fail closed.

The parser accepts the current Stable publisher's `## Custom release metadata`
section with `upstream_sha=...`, plus the historical HTML metadata block with
`Upstream SHA: ...`. Duplicated/mixed metadata, invalid source IDs and incomplete
or conflicting automation states are rejected. A fixture generated by the real
`build_release_body()` is executed by the Rust policy tests, so producer/consumer
format drift cannot silently make all updates unavailable again.

Revalidate latest and the selected asset immediately before downloading. Keep
HTTPS verification enabled, restrict redirects to GitHub delivery hosts, and
bound response sizes and timeouts. Download into an application temporary
directory, verify size and SHA256, and verify again before installer handoff.
Failed/corrupt downloads are removed; verified files remain in the temporary
cache for installer use and normal cache cleanup.

This is GitHub HTTPS/API integrity, **not independent update-signature
verification**. Independent signatures are deferred. Existing Android production
signatures remain unchanged. The upstream official signature verifier is retained
separately; custom updates use an explicit API-integrity path. This client uses
system/environment HTTPS proxy configuration rather than custom connection-proxy
settings.

The update setting opens a manual check/retry dialog; the startup-check preference
remains available. Download and opening the system installer each require a user
action. Unattended official/root installers are disabled for custom builds and
their old auto-install setting is replaced by the check entry. Windows opens the
matching EXE/MSI, macOS opens the unsigned DMG, Linux opens the package manager's
handler, and Android uses a private-cache FileProvider URI. Android retains system
unknown-source consent and package/signature checks. Native/device installation
must be tested separately; a successful handoff does not prove upgrade success.

## Temporary publication and first installation

Publish the selected Stable Release for the update window. Drafts are unavailable
to ordinary clients. Hiding the newest Release can make GitHub latest select an
older still-published release; version comparison prevents a downgrade. With no
suitable visible candidate, display temporary unavailability or no newer compatible
release and allow retry. Keep the Release visible until downloads/retries finish.
A fully downloaded, verified file can be installed after the Release closes.

Install the first client with this logic manually. Existing binaries retain their
old update source. Validation includes the client update contract, prepared-source
contracts, both patch generations/variants, Flutter analysis and affected release
contracts. Policy/backend tests do not establish real package or device behaviour.
