# Content-version release integration (phase 3)

Stable now reads the selected generation's manifest via the same `content.inputs` used by Nightly. It never allocates from GitHub Release counts. The exact target is `v{upstream}-custom.{patchset_version}`. Manifest hashes and reviewed Changelog must match before resolution succeeds. A complete exact matching modern release still passes the existing inventory, size, GitHub SHA256 and SHA256SUMS gates before reuse. A different identity under the same tag fails with `IMMUTABLE_TAG_BUILD_IDENTITY_COLLISION`; policy changes do not mutate revision, tags, signatures or Drafts.

The shared Coordinator BuildIdentity adds policy version 2, binding Patchset Version and a conservative SHA256 inventory of repository-controlled build inputs. Its immutable Git-ref journal, compare-and-swap, fencing, unknown-attempt budget, retry classification and cooldown implementation remain shared and unchanged. SourceIdentity retains the historical content key; the build key distinguishes N from N+2 when content returns to old bytes. Stable channel v5 and Nightly v2 digests are byte-aligned with this shared core. Policy-v1 keys and historical Stable v4 / Nightly digests retain exact old serialization. Stable Lock v2 freezes the new content and policy fields; the historical router still recognizes v1 locks.

Build policy includes non-contract scripts, metadata/build, platform and signing policies, local actions, requirements and actual build/prepare/Tag/Nightly workflows. Docs, revision history and router schedules do not affect it. It is a conservative repository-input fingerprint, not proof of binary reproducibility or full runner-image attestation. Effective public branding Variables retain the existing frozen source snapshot/provenance gate; v2 does not claim to attest undeclared external runner/tool downloads or give Variable changes a new release revision. Before activation, review effective external inputs and their pinning. Same tag remains immutable regardless of which input changed.

Legacy evidence is not reinterpreted as modern content history. A known historical producer with the same source under the new schema yields REVIEW_HOLD, not a fresh reservation or an invented success alias. Unknown historical evidence continues to hold. An empty new identity journal cannot authorize migration.

Both Notes paths use deterministic structured manifest data: current Common/SOS feature inventory, recorded revision delta, reason, classification, references, compatibility, limitations and hashes. The official upstream changelog remains distinct. Metadata still records upstream SHA, Build Identity, artifact and signing status. Nightly says explicitly that the recorded delta is not a claim of new changes in that build. Nightly resolves the latest successful official run as before; no public run/SHA pin input is added and no build mutates Patchset revision.
