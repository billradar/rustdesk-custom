## Source and package boundaries

The Linux/macOS reusable core generates one separate `macos-arm64-bridge-RUN` artifact only when the exact reviewed source requires the new SDK. It executes the existing reviewed Linux bridge recipe with Flutter 3.44.8, Rust 1.75, cargo-expand 1.0.95 and FRB 1.80.1. The native build uses the official 3.44.9 SDK. The generator has Contents read only and no signing Environment or production signing inputs. Native workers use Coordinator Lite's trusted Stable/Nightly context check followed by separate source and artifact verification. Existing Windows ARM64 code and artifacts are unchanged. Older sources skip the generator dependencies and artifact path.

Before compilation each native Mac ARM worker checks the same-run bridge's upstream/custom/run identity, helper/SDK versions and six file digests. The reviewed helper changes only `flutter/lib/common.dart` and `flutter/pubspec.yaml`; the six generated bridge files are then restored. A separate receipt binds their before hashes to the immutable prepared manifest, their after hashes and bridge identity, the source variant and exact recipe. The prepared manifest is never rewritten. Subsequent recipe checks reconstruct the reviewed inputs from the exact Git HEAD, rather than treating the transformed pubspec as a new interface. Current protected recipe files must still match the prepared inventory. Native runner architecture and actual Flutter version are checked independently.

Packaging carries this receipt to aggregation. The prepared workflow hash and approved signature independently require a receipt, so clearing the new flag or claiming the older SDK cannot evade validation. A Mac ARM 3.44 package must have the matching source/custom/run/variant/toolchain and bridge receipt, as well as the existing package checksums, native API/configuration probe, architecture and actual DMG/library gates. Desktop signing policy remains unchanged. Standard/SOS matrices, Wayland and Android production signing/publication gates are unchanged. Existing x86_64 and old-source Mac builds keep their old SDK and Flutter patch step; only the reviewed modern ARM path disables SwiftPM and omits the obsolete SDK patch.

## Validation and recovery

The official ARM build step changes the deployment target from 10.14 to 12.3 in `build.py` and `Cargo.toml`. Pre-build recipe checks still require their exact prepared bytes. Only the post-build packaging check reverses those two exact substitutions in memory and compares the resulting hashes to the unchanged prepared manifest. It requires the new target exactly once in each file; another target, extra code/features, changed bridge bytes or other protected recipe drift remains a hard failure. No file is excluded from verification, and no manifest or receipt is rewritten to accommodate build-time changes. Run 41549385808 exposed the missing post-build distinction after generating both ARM DMGs; the failed packages were not aggregated or published.

## Runner image migration

The macOS 14 ARM64 image retired on November 2, 2026. Active build targets now use `macos-26` for ARM64 and `macos-26-intel` for x86_64. `metadata/platform/runner-migrations.json` records these effective labels separately from the immutable upstream runner values; adapter signatures continue to bind the exact upstream workflow matrix. Mac ARM receipts also bind both labels. This migration changes the build host image only; it does not change the ARM64 deployment target of macOS 12.3 or the Intel target inherited from upstream. New native build evidence on both macOS 26 images is required before claiming the migrated image recipes have passed.
