## Current execution and ownership

- Stable and Nightly resolve/admit exact upstream and patch identities, use `prepare-source.yml`, then call shared platform and Android/Windows workers. #274 ordinary CI selects the exact v3 baseline in `metadata/build/ci-upstream-baseline.json`; the separate upstream main monitor checks moving HEAD. The formal v4 route uses restricted prepared source and tests a 13-target, non-release matrix with fixture reports and same-run aggregation.
- `prepare.sh` initializes an empty worktree, shallow-fetches, resolves/checks the commit, detaches, recursively initializes submodules, then checks gitlinks and worktree state. The fetch, checkout and verification presently run once. Recursive submodule setup may partially materialize a checkout and has no outer replay.
- `run_platform.py` runs the relevant build script once, emits redacted output and writes a target diagnostic with its exit code. Android verifies Standard-only, applies the Flutter SDK patch, builds dependencies and the Rust native library, then uses the reviewed Flutter command for a test-signed APK. The reviewed packaging step edits Gradle configuration, stages native libraries, invokes one Flutter APK command for the selected ABI, and moves the output. Flutter can internally repeat Gradle once for dependency retrieval. Production YubiKey signing runs in a separate gated job. Mac uses reviewed setup, vcpkg and build commands. ARM64 has independent bridge and transform receipts. Mac's official build includes deployment-target mutations and must not be replayed. Linux and Windows use their existing build recipes.
- The Android SDK installer owns three attempts with a 300-second subprocess limit per attempt, staged downloads, precise invalid-component cleanup and integrity checks. Cargo normally uses Cargo's configured retry policy (default three retries) and HTTP timeout (default 30 seconds); Cargo's external git transport has separate behavior. Gradle, Pub, vcpkg and other dependency action transport behavior is version-specific and was not measured in this audit. vcpkg `doNotCache: true` remains in place.
- The completed-event observer records runner capacity, runner shutdown and SDK installation failure and may request one target rerun under existing trusted Stable/Nightly rules, up to three GitHub run attempts. Its evidence goes to the existing report/dashboard. Router accounting covers separate workflow runs for an existing build identity (three, with six-hour cooldown). These limits are not a shared budget and there is no cross-run coordination for a new L1 retry. Automatic POST retry is outside Phase 1. The dependency DAG can reach downstream signing or draft creation after a recovered job. Expanding its authority requires a separate DAG and side-effect audit.

## Phase 1 design and verification

Apply one operation allowlist and versioned policy to three narrow call sites. The shallow upstream fetch can safely repeat in the same private Git directory before checkout. Mac Intel may prefetch the locked target dependency graph before the upstream build step with Cargo's own retries disabled for the prefetch and Git CLI enabled. Cargo and the approved build recipe still enforce their normal build behavior. Android keeps the Gradle edits, native copy, and APK move outside the retry boundary. Only a verified Maven Central 429 during Gradle compile classpath resolution qualifies, with the package output location checked before replay. Limit the Flutter boundary to one outer replay to bound its internal retry. The base delay is 240 seconds with upward jitter up to 20% (240–288 seconds total). Preserve the raw failure and existing release, source, bridge, and package gates.

Recovery is active only in the credential-free full-validation canary. Other POSIX shared call sites observe without adding execution deadlines or recovery; Windows Git Bash uses its original command. The active execution budget is monotonic and scoped to one operation in one job, including waits, execution and cleanup allowance. Retry events carry controlled fields only. No new network categories are eligible for workflow reruns. Unknown, deterministic and mixed failures remain failures. No cache writes or external fault injection are introduced.

Use offline fault injection for classifier, timing, output safety, policy validation, process cleanup, and retry decisions, plus the existing observer, SDK, router, prepared-source, qualification and bridge contracts. Run full platform validation at the resulting PR head before judging recovery ready. Stable and Nightly formal dry-runs need separate evidence. Production signing, runtime remote sessions, Windows process supervision and release publication are outside this canary.

Successful hosted recovery under rate limiting remains to be observed.

## Later phases and rollback

Phase 2 inventories immutable dependency identities (toolchain, lock/config, OS, arch/ABI and trust domain), then measures request volume, hits and corruption. Production never restores unverified PR data. Credentials, signing, sensitive objects and release outputs are ineligible. Phase 3 adds measured watchdog diagnostics and audited checkpoints keyed to exact source, recipe, target and run identity. Phase 4 incorporates operation evidence into existing summaries and measures first/final success, recovery yield, added latency, cache hits and missing evidence. Phase 5 evaluates service concurrency and shared mechanisms only after collecting representative data.

Disable canary recovery by removing the test-job mode setting, or revert the Phase 1 commit. Reverting the RFC is independent. Existing observer control remains `BUILD_INFRA_AUTO_RETRY_ENABLED`. None of these controls grants admission or bypasses a verification gate.
